# DECISIONS.md — Material assumptions and approved decisions

| ID | Decision | Status | Rationale / impact |
|---|---|---|---|
| D-001 | Stage 2 supports Sales Invoice, Purchase Bill, Cash Receipt, Cash Payment, General Journal, and manual Adjustments. Each is one balanced journal entry. | approved | Keeps transaction and journal consistency; avoids duplicate source records. |
| D-002 | Seed a minimal editable Chart of Accounts across the five categories. | approved | Immediate usability without locking users into a rigid COA. |
| D-003 | Currency is selected during onboarding, stored with the workspace, and used for formatting only. | approved | Avoids multi-currency complexity and jurisdiction assumptions. |
| D-004 | One report/workspace per local installation. It is not an accounting period. | approved | Matches the requested naming step; period close is deferred. |
| D-005 | Single user, no login, server bound to `127.0.0.1`. | superseded by D-022 | Local-first MVP; no shared or remote access. Stage 3 adds a local username/password gate while keeping the loopback default. |
| D-006 | Ledger-paper visual system with system fonts only. | approved | Professional accounting feel; no external assets or font requests. |
| D-007 | Dashboard provides a financial snapshot and trial balance. Formal statements, exports, period close, and automated adjustments are deferred. | approved | Fits the five required screens; avoids statutory assumptions. |
| D-008 | Reversal is the only correction path. One reversal per posted entry; reversal entries cannot be reversed. | approved | Preserves an auditable chain and prevents reversal loops. |
| D-009 | No tax, VAT, statutory, or jurisdiction-specific logic. | approved | Explicit non-goal from the requirements. |
| D-010 | Runtime is WSL Ubuntu + Node 24.22 + Express 5 + built-in `node:sqlite`; project at `/home/derp_28/accounting-app`. | superseded by D-032 | Verified environment; avoids native modules and Windows UNC issues. Superseded on 2026-10-24 when the user asked for the project to run locally in its Windows folder. |
| D-011 | Playwright is a dev-only dependency for UI/E2E checks. | approved (launcher superseded by D-032) | Chromium is launched through `scripts/test-e2e.mjs`, which keeps the optional Linux user-local library path. Edge headless screenshots remain a fallback. Does not affect runtime. |
| D-012 | Stage 1 used in-memory mock state with no browser storage. | approved (historical) | Prevented misleading persistence in the prototype. Stage 2 replaces it with SQLite persistence. |
| D-013 | Stage 1 posted entries were immutable; a simulated reversal created a linked mock entry. | approved (historical) | Demonstrated the correction workflow in the prototype. Stage 2 implements the same rule with database triggers and linked posted entries. |
| D-014 | No formal reports page; the dashboard contains category totals and trial balance. | superseded by D-024 | Five-screen navigation is preserved in Stage 2; Stage 3 adds a Reports page with trial balance, income statement, and balance sheet. |
| D-015 | Chart of Accounts seed codes use the hundreds series and increment by one within each category: assets 100 Cash, 101 Accounts Receivable, 102 Prepaid Expenses, 103 Equipment; liabilities 200 Accounts Payable, 201 Accrued Liabilities; equity 300 Owner's Equity; revenue 400 Service Revenue; expenses 500 Operating Expenses, 501 Rent Expense. | approved | Originally seeded with gaps (100, 110, 120, 150, 200, 210, 300, 400, 500, 510). On 2026-10-20 the user requested Cash 100, Accounts Receivable 101, and +1 sequencing. Migration `004_sequential_seed_codes.sql` renumbers the seeded rows while keeping account IDs stable; category ranges are preserved. |
| D-016 | Deactivating an account blocks new drafts and postings, but a posted entry that already uses that account may still be reversed. | approved | Confirmed by the user on 2026-10-20. A reversal is a correction, not new use. Blocking it would strand an incorrect posted entry with no allowed correction path. Covered by the lifecycle integration test. |
| D-017 | The entry API stores integer cents. It accepts `debitCents`/`creditCents` first and falls back to decimal `debit`/`credit` strings with at most two places; values are parsed exactly, never as binary floats. | implemented | Keeps the browser/server boundary explicit while allowing exact decimal input. Unit and HTTP tests cover conversion and excess-precision rejection. |
| D-018 | User-created account codes must be three-digit numbers inside their category's hundred series: assets 100–199, liabilities 200–299, equity 300–399, revenue 400–499, expenses 500–599. Codes are unique. | approved | Confirmed by the user on 2026-10-20 with range enforcement. Server validation and database triggers reject out-of-range codes; all seeded codes already comply. |
| D-019 | A reversal is dated with the server's current UTC date, uses source type `GENERAL_JOURNAL`, and keeps the required reversal reason. | approved | Confirmed by the user on 2026-10-20. The requirements do not define a separate reversal-date or source-type policy; this keeps the correction in the current ledger period and visible in the journal. |
| D-020 | Workspace setup is a dedicated full-screen Step 2 after registration, not a dialog layered over the dashboard. At widths of 1000 px or less, the workspace form starts at the top of the viewport and the decorative panel is hidden. | approved | Requested by the user after the setup step appeared below the page instead of in front. The full-screen step removes native-dialog placement and background-scroll ambiguity; E2E verifies no open dialog and an above-the-fold card at 390 px. |
| D-021 | When adding an account, the code field is prefilled with the next unused code in the selected category (highest existing code + 1, starting at the category minimum). The prefilled code remains editable and must still pass category-range and uniqueness validation. Changing category before typing a code refreshes the suggestion; editing the code stops automatic replacement. | approved | Follows the user's 2026-10-20 request for +1 account codes and editable auto-fill. The client computes the convenience value, while the server and database triggers remain authoritative. |
| D-022 | Stage 3 adds a **local** username/password gate. Passwords are stored as salted scrypt hashes compared in constant time. Sessions are server-side rows; the browser holds an `HttpOnly`, `SameSite=Strict` cookie (`Secure` only when `LEDGERLINE_SECURE_COOKIES=1`). Mutations require an `X-CSRF-Token` matching the session token. Five failed sign-ins lock the account for 15 minutes. Sessions idle-lock after 30 minutes and expire 12 hours after sign-in. There is no public registration, no email recovery, and no reset link; `npm run auth:reset-password -- <username>` resets the password and revokes every session. | approved | Confirmed local login (Option B) by the user. Protects the running app without turning it into a network service. The password protects the app, not the SQLite file; data-at-rest protection remains full-disk encryption. |
| D-023 | One local account per installation can own **multiple ledgers** (separate sets of books). There is no multi-user, role, or membership model. Ledgers are chosen at first run and created/switched from the sidebar. | approved | Matches the user's "one local user, many ledgers" model without the cost of roles or sharing. |
| D-024 | Stage 3 adds a **Reports** page with three tabs: trial balance, income statement, and balance sheet. Every report has a shared **Adjusted / Unadjusted** basis toggle, defaulting to Adjusted. | approved (supersedes D-014) | The user asked for unadjusted and adjusted trial balance plus income statement and balance sheet. One toggle keeps the basis consistent across all three. |
| D-025 | The balance sheet shows a computed **Accumulated earnings** line (all posted revenue minus expenses through the as-of date) because there is no period close. The line is labeled as computed. | approved | Without closing entries there is no posted retained-earnings balance; computing it keeps the sheet balanced and honest. |
| D-026 | Migration `005_local_auth_multi_ledger.sql` creates an unclaimed placeholder user (`user-local`) and a `ledger-default`, and assigns all pre-existing data to `ledger-default`. First-run setup claims the placeholder and renames the ledger; a fresh installation starts from an empty database with only the seeded Chart of Accounts. New ledgers receive fresh seeded accounts from `DEFAULT_ACCOUNTS`. | approved | Preserves an existing local database across the upgrade while guaranteeing that distributed copies start empty. |
| D-027 | Journal entry numbering stays **global** (one `number_sequences` row per source prefix) rather than per ledger. | approved | Avoids rebuilding `journal_entries` and keeps migration risk low; entry numbers remain unique and readable. Per-ledger numbering is not required by the user. |
| D-028 | The single local user is enforced by the database trigger `trg_single_local_user`, in addition to the service layer. | approved | Makes the one-account rule a database invariant rather than only an application convention. |
| D-029 | Distribution is **source on GitHub plus self-hosted copies**. The repository stores only source; `data/` and `.env` stay git-ignored. Releases publish a container image to GHCR and a GitHub Release. There is no public hosting, no landing page, and no hosted database. Every clone, container, or release copy starts with a fresh empty database. | approved | The user does not want public hosting and wants downloadable/self-hosted copies while preserving local data locally. Storage-only sources (GitHub Pages, Vercel) cannot run the Express/SQLite app. |
| D-030 | The server still binds `127.0.0.1` by default and refuses non-loopback hosts. Container mode may bind `0.0.0.0` only when `LEDGERLINE_CONTAINER=1`; the compose file publishes the host port on `127.0.0.1` only. | approved | Lets Docker forward the port without turning the app into a network service by accident. Same-origin Host/Origin checks remain in force. |
| D-031 | Report defaults: trial balance and balance sheet default to **today** as the as-of date; the income statement defaults to the **current month** (first of the month to today). Dates and basis remain user-adjustable. | approved | Matches common accounting practice and the user's request for as-of/period filtering. |
| D-032 | The project is localized to this folder and runs on Windows Node 24 (verified with 24.15.0) with no WSL, NVM, or absolute home path. Runtime behavior lives in cross-platform `scripts/*.mjs` entries; the `scripts/*.sh` files are thin delegators for Linux/WSL/CI, and Playwright's `webServer` launches `scripts/e2e-server.mjs`. Every script resolves the project root from its own file, so paths with spaces and any working directory work. | approved | Requested by the user on 2026-10-24: the WSL copy at `/home/derp_28/accounting-app` did not exist and the copied tree had lost its executable bits, so the documented runtime could not start. One implementation per command avoids drift between Windows and Linux. The accounting rules, security model, loopback binding, and distribution design are unchanged. |
| D-033 | The transitive `body-parser` dependency is patched from 2.3.0 to 2.4.0 to clear GHSA-27r3-jxmh-p828 (high: DoS via trailing bytes after a compressed request body). `package.json` dependency ranges stay unchanged (`express ^5.3.0`, `@playwright/test ^1.64.1`); only `package-lock.json` records the patched resolution. | approved | Found by `npm audit` during the Windows localization run, after the Stage 3 evidence was recorded. 2.4.0 is inside Express's existing semver range, so no Express upgrade or code change is needed. The full suite was re-run on the patched tree because JSON body parsing is on every API path. |
| D-034 | A **GitHub Pages interactive demo** is published at `https://derp28.github.io/AccountingSystem/`. It reuses the real `public/` UI unchanged and answers `/api/*` from an in-browser engine (`demo/api.js`) seeded with books generated through the real services against a real SQLite database (`scripts/build-demo.mjs`). Demo data lives in browser memory only, resets on reload, is never sent anywhere, and accepts any password on the sign-in screen. The site is built by `.github/workflows/pages.yml` on every push to `main` and force-published to the `gh-pages` branch, which Pages serves; `docs/` is generated output and stays git-ignored. | approved (supersedes the "no public hosting / no landing page" clause of D-029) | The user asked for a public demo after the project was pushed to GitHub. Pages is static hosting, so the Express/SQLite app cannot run there and the demo must not claim persistence. Importing the server's own `server/lib/validation.js`, seeding through the real posting services, and rewriting every persistence sentence in the demo build keep the demo honest and prevent accounting-rule drift. Publishing from a `gh-pages` branch (rather than `actions/deploy-pages`) is what the Actions token can do without repository-admin rights: `configure-pages` with `enablement: true` failed with the default token, while pushing the branch enabled Pages automatically. Self-hosted distribution, local-only binding, and the SQLite runtime are unchanged. |
